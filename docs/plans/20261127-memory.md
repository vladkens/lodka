# Memory back to the Mac

A guest that used memory and is done with it gives it back, so lodka's footprint in Activity Monitor follows what the guest holds rather than its peak: a virtio-balloon device with free page reporting, guest RAM the Mac can take back piece by piece, and the guest trimming its own page cache when idle. Done when, on the test Mac, a build that grows the guest by several GiB and then goes idle brings lodka's footprint back near its idle baseline within a minute for freed memory and within some minutes for the page cache, the earlier benchmarks lose nothing under load, and memory the VMM touches for the guest is no longer counted twice.

## Decisions

- Guest RAM is 2 MiB pieces, each a memory object of its own (`mach_make_memory_entry_64` with `MAP_MEM_NAMED_CREATE | MAP_MEM_LEDGER_TAGGED`), placed side by side with `mach_vm_map(FIXED | OVERWRITE)` and mapped into the VM once. Addresses stay contiguous. Ledger-tagged memory is what `hv_vm_allocate` makes: a page both the guest and the VMM touched counts once in the footprint, where one `mmap` counted it twice (1 GiB showed as 2 GiB).
- A reported range that covers whole pieces gives them back: `hv_vm_unmap`, a fresh object at the same address, `hv_vm_map`; footprint and the Mac's free memory change at once. A piece given back is made again of 64 KiB parts, each an object of its own, that later go back one by one: after a build the guest's free memory lies in blocks of 16 KiB–1 MiB around the slab and page cache left in nearly every 2 MiB piece, which compaction doesn't gather, and with whole pieces only the footprint stayed 1.7–2.2 GiB above idle. RAM isn't made of parts from the start: 1.4 µs an object, which threads don't speed up (the task's map lock), is 175 ms of start for 8 GiB; the balloon's thread makes them as the guest's first reports come in. Each object costs the kernel 320 bytes, 40 MiB for 8 GiB. What is left of a range, rounded inward to 16 KiB (macOS rounds madvise outward and would take neighbours), gets `madvise(MADV_FREE)`: macOS takes those pages when it needs them. `MADV_DONTNEED` does nothing on macOS and `MADV_FREE_REUSABLE` miscounts once the guest writes the page again; replacing part of one large mapping leaks the replaced pages.
- virtio-balloon (5) with `VIRTIO_BALLOON_F_REPORTING` only: queues inflate, deflate and reporting at 0, 1, 2, as Linux's virtio-mmio numbers the present ones (the spec's fixed index 4 is an open mismatch), each of 64 entries (the driver wants 32 at least). No inflation: the balloon's target stays 0. Each report is a chain of free blocks the device gives back, then returns.
- The guest reports blocks from 16 KiB up (`page_reporting.page_reporting_order=2`, the Mac's page size), not from 2 MiB, the 6.18 default, at which page cache freed page by page never comes back. Linux 6.18 reports every 2 s, a sixteenth of the free blocks each time; no patch for a shorter delay unless measured too slow.
- The page cache is the guest's to trim: `lodka-guest`, once the guest is idle (little CPU, no I/O and no memory pressure for two minutes), writes to the root cgroup's `memory.reclaim` a step of inactive file pages every 10 s (`swappiness=0`), down to a floor of a few hundred MiB, and stops for an hour when what it took comes back as refaults. Then `compact_memory` once, so the freed pages form whole pieces. Never `drop_caches`: virtio-fs caches the Mac's names for an hour, and inodes are the costly part to read again.
