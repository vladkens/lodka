# Virtio and the guest's disks

The guest boots from a root file system of its own: virtio over MMIO with the console, entropy and block devices, an erofs root from Alpine's packages, and `lodka-guest` as PID 1 with the ext4 data disk at `/var/lib`. Done when, on the test Mac, the guest boots to PID 1 with its console on hvc0, makes the data disk's file system on the first boot, finds it on the next, after a kill too, and grows it when the setting does.

## Decisions

- Devices are virtio over MMIO (version 2): no PCI to emulate, and the device tree lists them. lodka raises their interrupts as level-triggered SPIs in HVF's GIC.
- Each device serves its queues on a thread of its own, woken by the guest's notify; the block devices have a queue and a thread per vCPU. A device takes no notifications while it drains a queue and raises no interrupt the driver asked to skip. A reset stops a device's use of its queues; a started device doesn't start again (its threads keep their queues, and the guest resets devices only as it powers off), so a driver bound to it again finds it needs a reset.
- Reads and writes go straight between the disk file and guest memory (`preadv`/`pwritev`). Requests are bounded by the disk's size, console output by a fixed buffer.
- A flush is `F_BARRIERFSYNC`, not `F_FULLFSYNC` (Rust's `sync_data` on macOS): earlier writes reach the disk first, so the guest's journal holds across a power loss, at a quarter of the cost.
- The guest's root is erofs (lz4hc), read-only; `/etc` is an overlay in memory, `/var` a tmpfs with the data disk at `/var/lib`. The data disk is a sparse file with discard, so space the guest frees is given back.
- One VM at a time on the disk: the VM's process holds a write lock on its pid file as long as it runs, and a second one stops at once.
- The data disk gets a file system only while it is blank; a disk with data but no ext4 stops the boot.
- A larger data disk is grown at boot by the guest's own `EXT4_IOC_RESIZE_FS` on the mounted file system; `resize2fs` refuses it as busy.
- `lodka-guest` is static for musl, linked by Rust's own `rust-lld`, so the Mac builds it without a cross toolchain; the rootfs is made from Alpine's packages in a container, `make images`.

## Result

On the test Mac (M2, macOS 27), 4 vCPUs and 2 GiB: from `lodka _vm` to the data disk mounted in 0.06–0.10 s, 0.1 s of CPU time in the first 10 s. The first boot made the file system on the 16 GiB disk, which takes 145 MiB on the Mac; a boot after a kill found it with its journal replayed; set to 20 GiB, the next boot grew it. The rootfs is 2.4 MB.
