# The machine

lodka's own VMM on Hypervisor.framework boots the guest's Linux kernel: `lodka _vm` loads the `Image` with a device tree and runs it on every vCPU until it powers off or restarts. Done when, on the test Mac, the kernel built from `guest/kernel.config` brings up all vCPUs, sets its clock from the PL031, logs through the PL011 and gets as far as mounting its root, which it has none of yet.

## Decisions

- Hypervisor.framework, not Virtualization.framework: the VMM is ours, so the devices, the file sharing and the hypercall fast path are too (OrbStack's way). Its in-kernel GICv3 (macOS 15+) does the interrupt routing.
- The guest's layout is QEMU `virt`'s (PL011 at 0x09000000, PL031 at 0x09010000, RAM at 1 GiB) but the GIC sits at 0x10000000: its redistributors' space is sized for 256 vCPUs, 32 MiB, more than `virt` leaves. All vCPUs are made before any runs, as the GIC's topology is final once one does.
- The kernel is the `Image` booted straight with a device tree, no firmware; PSCI over HVC starts and stops the vCPUs and powers the VM off.
- HVF runs WFI and the virtual timer in its kernel (no such exits measured on macOS 27); the VMM's WFI path is kept for when it exits.
- The kernel is `allnoconfig` with the options lodka's machine needs, built in an Alpine container; the build fails when an option is not applied.
- `lodka _vm` runs the VM in the process that starts it, with the settings in `lodka.conf`; the binary needs the hypervisor entitlement (`codesign --entitlements`). A restart stops the VM: a process has one VM, so the next takes a new process.

## Result

On the test Mac (M2, macOS 27), 4 vCPUs and 2 GiB: `lodka _vm` boots the 4.8 MB kernel to its panic at the missing root and stops in 0.02 s. The log shows all 4 vCPUs up through PSCI, the clock set from the PL031, and the console on the PL011 (`ttyAMA0`).
