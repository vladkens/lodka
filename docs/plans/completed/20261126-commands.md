# The commands

lodka is used through its commands: `lodka start|stop|status|ssh|delete`, with the VM in a process of its own. Done when, on the test Mac, a cold `lodka start` reaches Docker, `docker run` with a published port answers on localhost and `::1`, `lodka ssh -- uname -a` answers, `lodka stop` powers the guest off cleanly, a reboot in the guest brings it back, `lodka delete` removes the disk, and the boot time and idle CPU are measured against OrbStack.

## Decisions

- `lodka start` runs `lodka _vm` in a session of its own with its output in `lodka.log`, and returns once Docker answers on its socket. The binary signs itself ad hoc with the hypervisor and virtualization entitlements the first time.
- The commands ask the VM's lock, the write lock on its pid file the VM's process holds as long as it runs: the kernel, not the file's text, says who holds it. `lodka delete` takes it while it deletes the disk. The sizes given to `start` reach the VM in an environment variable and are saved only by the VM that got the lock.
- A reboot in the guest runs the next VM in the same process: `exec` with the lock's descriptor kept open, so no `stop` or `delete` gets in between.
- `lodka ssh` logs in as root with lodka's own key, made on first use and sent to the guest over the control channel at each boot. sshd's host key lives on the data disk, made on the first boot and synced at once.
- Ports: the guest reports the TCP ports it listens on for every address when they change, and again every 10 s so lodka retries a port taken on the Mac; lodka listens on 127.0.0.1 and ::1 for each, and sends each connection over vsock to the guest's port 1026, which joins it to the port on the guest's loopback. Not to the guest's address: macOS lets a process reach the vmnet network only with the Local Network permission, which `lodka _vm` started from a shell lacks.

## Result

On the test Mac (M2, macOS 27), both with 2 vCPUs and 6 GiB, lodka against OrbStack:

- Start to `docker info`: 0.63 s against 0.73 s; stop 1.3 s against 1.2–1.8 s.
- Idle CPU: 0.23 s against 0.19 s of CPU time in 30 s.
- `docker run --rm alpine true`: 177 ms against 204 ms.
- fio on a volume, 4 KiB: random reads at depth 32 461k IOPS against 429k, 4 jobs 941k against 788k; random writes 11–23k against 14–15k; write and fsync 360–1830/s against 246–364/s, both varying from run to run.
- Random reads at depth 1: 36–56k IOPS against 491k. Each lodka read is completed by an interrupt (56k when fio runs on the vCPU that takes it); OrbStack's guest completes them with almost none.
- Through a published port: a 1 GiB download at 4.3 GB/s against 7.2 GB/s; a request on a new connection 0.39 ms against 0.36 ms.
- A reboot in the guest keeps the VM's process: Docker answers again in 2.1 s.
