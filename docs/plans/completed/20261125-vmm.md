# Our own VMM with Docker

`lodka start` boots the guest on lodka's own VMM on Hypervisor.framework and answers on Docker's socket; `lodka ssh`, `stop`, `status` and `delete` work, containers' ports answer on localhost. Done when, on the test Mac, a cold `lodka start` reaches Docker, `docker run` pulls and runs an image with a published port reached on localhost, `lodka ssh -- uname -a` answers, `lodka stop` powers the guest off cleanly, and the boot time and idle CPU are measured against OrbStack.

## Decisions

- Hypervisor.framework, not Virtualization.framework: the VMM is ours, so the devices, the file sharing and the hypercall fast path are too (OrbStack's way). Its in-kernel GICv3 (macOS 15+) does the interrupt routing; lodka raises device interrupts as level-triggered SPIs.
- The guest's layout is QEMU `virt`'s (PL011 at 0x09000000, virtio at 0x0a000000, RAM at 1 GiB) but the GIC sits at 0x10000000: its redistributors' space is sized for 256 vCPUs, 32 MiB, more than `virt` leaves. All vCPUs are made before any runs, as the GIC's topology is final once one does.
- Devices are virtio over MMIO (version 2): no PCI to emulate, and a device tree lists them. Each device serves its queues on a thread of its own, woken by the guest's notify; the block devices have a queue and a thread per vCPU. A device takes no notifications while it drains a queue and raises no interrupt the driver asked to skip.
- HVF runs WFI and the virtual timer in its kernel (no such exits measured on macOS 27); the VMM's WFI path is kept for when it exits.
- The network is vmnet's shared mode through the macOS 26 API, which a process signed with the virtualization entitlement may start without root (checked on this Mac); vmnet gives NAT, DHCP and DNS, and the Mac reaches the guest's address. macOS 26's API ignores the interface id: each start gets a new MAC address and subnet. The guest probes the path MTU, as a network that drops full-size packets silently (the test Mac's, 1420) stalls TLS otherwise.
- Docker's API goes over vsock (lodka dials the guest's port 1025 for each connection), not TCP on the shared network, which every process on the Mac could reach.
- Ports: the guest reports the TCP ports it listens on for every address when they change, and again every 10 s so lodka retries a port taken on the Mac; lodka listens on 127.0.0.1 and ::1 for each, and sends each connection over vsock to the guest's port 1026, which joins it to the port on the guest's loopback. Not to the guest's address: macOS lets a process reach the vmnet network only with the Local Network permission, which `lodka _vm` started from a shell lacks.
- The guest's root is erofs (lz4hc), read-only; `/etc` is an overlay in memory, `/var` a tmpfs with the data disk at `/var/lib`. The data disk is a sparse file with discard, so space Docker frees is given back.
- A flush is `F_BARRIERFSYNC`, not `F_FULLFSYNC` (Rust's `sync_data` on macOS): earlier writes reach the disk first, so the guest's journal holds across a power loss, at a quarter of the cost.
- A larger data disk is grown at boot by the guest's own `EXT4_IOC_RESIZE_FS` on the mounted file system; `resize2fs` refuses it as busy.

## Result

On the test Mac (M2, macOS 27), both with 2 vCPUs and 6 GiB, lodka against OrbStack:

- Start to `docker info`: 0.63 s against 0.73 s; stop 1.3 s against 1.2–1.8 s.
- Idle CPU: 0.23 s against 0.19 s of CPU time in 30 s.
- `docker run --rm alpine true`: 177 ms against 204 ms.
- fio on a volume, 4 KiB: random reads at depth 32 461k IOPS against 429k, 4 jobs 941k against 788k; random writes 11–23k against 14–15k; write and fsync 360–1830/s against 246–364/s, both varying from run to run.
- Random reads at depth 1: 36–56k IOPS against 491k. Each lodka read is completed by an interrupt (56k when fio runs on the vCPU that takes it); OrbStack's guest completes them with almost none.
- Through a published port: a 1 GiB download at 4.3 GB/s against 7.2 GB/s; a request on a new connection 0.39 ms against 0.36 ms.
