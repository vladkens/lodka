# The Mac's folders in the guest, fast

`/Users` in the guest at the same path, so `docker run -v "$PWD:/app"` works from any folder of the Mac user: a virtio-fs device whose FUSE requests lodka serves from macOS files. Done when, on the test Mac, git, npm, cargo and editors' atomic saves work on a bind mount as root and as a non-root user, a change made on the Mac shows in the guest at once and wakes a watcher there, and `npm ci`, `git status` and `find` on a bind mount are at least as fast as on OrbStack.

## Decisions

- A virtio-fs device (26) in `lodka-vmm`, one share per device: its tag and the Mac folder it serves. lodka shares `/Users`; the guest mounts it at `/Users`. The FUSE structs are written by hand from the kernel's `include/uapi/linux/fuse.h` (BSD-2-Clause), protocol 7.45.
- A node is a file's `(st_dev, st_ino)` with the guest's lookup count, never a path or a descriptor: lodka reaches it again through `fsgetpath`, opens with `O_NOFOLLOW_ANY` and checks the inode it got, and answers ESTALE when it is gone. Only open files and directories hold descriptors; a few directories' descriptors are kept for lookups.
- Names are matched byte for byte: on the case- and normalization-insensitive APFS a lookup of `readme.md` doesn't find `README.md`, so the guest's cache never has one inode under two names and `mv foo Foo` reaches the Mac as a rename.
- A directory is listed once per open handle with `getattrlistbulk`, which gives each entry's attributes with its name (READDIRPLUS); offsets are indices into that listing.
- The caller owns every file, as with Virtualization.framework, and macOS checks access as the Mac user: the guest kernel shows each process itself as the owner, so its attribute cache doesn't show one user's view to another, and checks no permissions of its own (a patch, see below). chown succeeds and changes nothing.
- Locks stay in the guest kernel: macOS's locks don't behave as Linux's, and the driver never interrupts a waiting one. fsync is `F_BARRIERFSYNC`, as for the data disk. `com.apple.*` extended attributes are hidden from the guest.
- Changes made on the Mac come from FSEvents with the inode of each, and go to the guest as FUSE notifications: the names, attributes and data that changed are dropped from its caches and inotify fires for them. So names, attributes and missing names are cached for an hour; without FSEvents, for a second. Linux 6.18's driver has no notification queue: lodka's kernel adds the spec's (`VIRTIO_FS_F_NOTIFICATION`, queue 1, a patch in `guest/patches/`, applied by `scripts/build-guest.sh`).
- A notification is on its way for a few milliseconds. An open of a file changed since the guest last got its attributes asks it to get them again (`FOPEN_INVAL_ATTR`, lodka's), so a read never sees new data cut at the old size; and a file the guest never looked up, written on the Mac, still wakes its directory's watchers (`VIRTIO_FS_INVAL_MODIFIED`, lodka's).
- A request a task waits for goes to its vCPU's own queue, after the request queues, and is kicked by an HVC with the device's MMIO base and the queue, which lodka serves on the vCPU's thread before it runs on: no wakeup of a device thread, no interrupt, no kworker. Readahead, writeback, fsync, lock waits, FORGET and requests over 128 KiB stay on the queues served by threads. Prior art: libkrun's `VIRTIO_FS_F_SYNC` (libkrun#933 and its kernel branch), here with an HVC instead of an MMIO notify, which runs outside the device's lock.
- `copy_file_range` copies on the Mac: `clonefile` only makes a new file, and the guest copies into one it has open.
