# A Docker context

`lodka start` adds a `lodka` context to the Docker CLI's config, so `docker context use lodka` works without `DOCKER_HOST`. Done when, on the test Mac, `docker context ls` lists `lodka` after a start, `docker --context lodka run` and, after `docker context use lodka`, a plain `docker ps` reach the VM, the context stays after `lodka stop`, and a start with another state folder points it at that folder's socket.

## Decisions

- lodka writes the context's file itself, as the Docker CLI keeps it: `$DOCKER_CONFIG/contexts/meta/<sha256 of the name>/meta.json` (`~/.docker` without the variable), with the endpoint `unix://` and the socket's path. No `docker context create`: the CLI may be missing or another version, and a start shouldn't wait on it. The file is written only when it changes, through a temporary file and a rename.
- lodka never switches the current context: `config.json` holds the person's choice and their registries' credentials, and lodka doesn't touch it. `lodka start` prints `docker context use lodka`, and `DOCKER_HOST` only when it couldn't write the context; `lodka status` shows the socket.
- The context stays after `lodka stop` and `lodka delete`: it names the socket's path, which the next start uses again. A failure to write it is a warning, not a failed start.
